# pbx Э3 — обратный поток: корп-состояние через служебную ветку зеркала (дизайн)

Дата: 2026-07-02. Статус: спроектирован автономно по одобренному роадмэпу
(«погнали Э3»); решения приняты мной, допущения помечены (§2.1) — пользователь
может скорректировать любое до/после реализации.

## 1. Контекст и цель

Этап Э3 дорожной карты (Э1 status ✓ → Э2 транспорт ✓ → **Э3 обратный поток** →
Э4 ctx/self-update). Прямой поток (дом → ноут) закрыт Э2. Слепое пятно:
дом ничего не знает о состоянии корп-репозиториев. Класс инцидентов SUP-2603
(устаревший домашний снимок молча откатывает чужую влитую работу) ловится
сейчас только deliver-guard-ом на ноуте — в самом конце конвейера.

Э3 закрывает пятно на этапе ПЛАНИРОВАНИЯ: на ноуте `pbx snapshot` снимает
состояние корп-реп (ветки, лог dev, ahead/behind доставленных веток) в
маленькие текстовые файлы и коммитит их в служебную ветку личного GitHub-
зеркала; дома `pbx corp` показывает эту картину человеку и ИИ ДО подготовки
доставки.

Факты разведки (2026-07-02, все механики проверены вживую research-агентами
на /tmp-фикстурах, git 2.34.1; два структурных утверждения дополнительно
выдержали независимую адверсариальную перепроверку; полный проверенный код —
`.superpowers/sdd/e3-research.md`).

## 2. Решения

- **Состояние живёт в служебной ветке `pbx/state` зеркала каждого проекта**
  (не в отдельном репо): та же auth-модель, что Э2 (PAT уже покрывает зеркала),
  ноль новой инфраструктуры; проекты без MIRROR вне охвата — как в Э2.
- **КЛЮЧЕВОЕ: у state-коммита НЕТ родителей из корп-истории.** Родитель —
  только tip самой `pbx/state` (parent-chain как в Э2 → push без --force).
  Проверено вживую с контрпримером: без корп-родителей в зеркало уезжает
  6 объектов (4 blob + tree + commit); с родителем-корп-HEAD push утаскивает
  ВСЮ достижимую корп-историю, и содержимое корп-файлов читается прямо из
  зеркала (16 объектов на фикстуре). Provenance — внутри файлов и в сообщении
  коммита, не в parent-ах.
- **Ноут: `pbx snapshot [проект]`** — без аргумента обходит все проекты
  реестра, у которых REPO — git И задан MIRROR (остальные — скип с пометкой);
  с аргументом — один проект, отсутствие MIRROR/REPO — die как в push.
- **Дом: `pbx corp [проект] [--json]`** — без аргумента все проекты с MIRROR;
  фетчит `pbx/state` в одноразовый tmp-репо (`--depth 1`), SRC не трогается
  вообще; рендерит человеку; `--json` — машинный сурфейс для ИИ.
- **Формат данных: 4 файла в корне дерева ветки** (§5): `state.json`
  (полное состояние, для ИИ — отдаётся `corp --json` без парсинга),
  `state.env` + `branches.tsv` + `log.tsv` (bash-парс дома, jq в системах нет).
- **Различение «снимка ещё нет» от «зеркало недоступно» — через `ls-remote`**
  (проверено: fetch даёт rc=128 в обоих случаях и не годится; `ls-remote`
  даёт rc=0 + пустой stdout при отсутствии ветки и rc=128 при недоступном
  репо — стабильный признак без парса stderr).
- **Кандидаты из ревью Э2 включены**: push-мета в `<проект>.meta` через новую
  `meta_update` (§7), MIRROR и push-инфо в `pbx status` (§8).
- Сетевые вызовы — обвязка Э2: `GIT_TERMINAL_PROMPT=0 timeout 30`
  (проверено: file://-fetch/push она не мешает).

### 2.1 Допущения (пользователь отсутствовал — скорректировать при желании)

1. Имена команд — из роадмэпа: `snapshot` (ноут) и `corp` (дом). Слово
   «снапшот» перегружено (в Э2 это снимок рабочего дерева) — в help/README
   формулировки разведены: push «снапшот кода», snapshot «снимок состояния».
2. Имя служебной ветки захардкожено: `pbx/state` (env-настройка — YAGNI;
   конвенция feature/… с ней не пересекается).
3. Порог протухания снимка в `corp` захардкожен: 24 часа (жёлтая пометка).
4. Глубина данных: лог dev — 20 коммитов; веток — 30 самых свежих по
   committerdate (родной `--count=30` у for-each-ref) + поле branches_total;
   diff веток — только `--shortstat` по three-dot (от merge-base; two-dot
   шумит встречными правками dev — воспроизведено).
5. Ветки «доставленного» класса: префиксы `feature/ fix/ hotfix/ bugfix/
   chore/` (та же конвенция, что предупреждение deliver).
6. `snapshot` пушит в зеркало ТОЛЬКО файлы состояния — git-объекты корп-
   истории не утекают (доказано), но текстовые метаданные (сабжекты, sha,
   имена веток) уезжают by design: состав полей ревьюился как публикуемые
   данные, содержимого диффов/файлов в состоянии нет. Исходники в этих же
   зеркалах уже лежат снапшотами Э2.
7. Пустой снапшот НЕ скипаем: каждое дерево содержит `generated_at` → каждый
   снапшот уникален и фиксирует сам момент съёмки (свежесть — это данные;
   скип по tree-sha, как в push, здесь не сработал бы и не нужен).
8. Меню пополняется обоими пунктами (§9); перенумерация тестов — как в Э2.

## 3. Реестр и конфиг

Новых ключей реестра нет: используется MIRROR из Э2 (на ноуте — тот же ключ в
ноутовском реестре; заполняется пользователем при переносе pbx). REPO на ноуте
уже задан. BASE_BRANCH (дефолт dev) — та ветка, чей лог и относительно которой
ahead/behind снимаются.

## 4. `pbx snapshot` — механика (проверено вживую)

Ядро: **коммит дерева из 4 маленьких файлов без касания корп-репо** —
рабочее дерево, индекс (sha1 бит-в-бит), HEAD, refs корп-репо не изменяются
ни в одном шаге. Подход mktree выбран вместо теневого индекса осознанно:
теневой индекс при забытом `GIT_INDEX_FILE` превращается в разгром реального
индекса (staged-удаление ВСЕХ tracked-файлов — воспроизведено на фикстуре).

1. `git -C REPO fetch origin --prune` (обвязка Э2). Сбой (нет VPN) —
   НЕ фатален: снимок продолжается по последним известным remote-refs
   с `fetch_ok=false` в состоянии (for-each-ref/rev-list на устаревших
   remote-refs работают — проверено); corp покажет предупреждение.
2. Сбор данных (§5) — только чтение.
3. Файлы пишутся в `mktemp -d`; блобы — `git -C REPO hash-object -w` строго
   с АБСОЛЮТНЫМИ путями (git -C делает chdir — относительный путь скрипта не
   найдётся); дерево — `git mktree` (формат stdin: `<mode> SP blob SP <sha>
   TAB <имя>` — TAB обязателен, пробел даёт fatal).
4. Наличие ветки: `ls-remote <MIRROR> refs/heads/pbx/state` — rc=128 →
   die «зеркало недоступно»; rc=0 + пусто → первый снапшот (root-коммит);
   иначе `git fetch <MIRROR> pbx/state` → FETCH_HEAD → родитель
   (`rev-parse FETCH_HEAD` сразу после fetch — FETCH_HEAD живёт до
   следующего fetch).
5. `commit-tree` с ЯВНЫМИ `GIT_AUTHOR_*`/`GIT_COMMITTER_*` (=pbx; конфиг
   user.name корп-репо не предполагается) → валидация SHA (`_pbx_is_sha`,
   грабля Э2 про удаление ветки пустым refspec) →
   `git push <MIRROR> <sha>:refs/heads/pbx/state` — назначение ПОЛНЫМ
   refname (короткое `sha:pbx/state` на несуществующей ветке падает:
   «not a full refname») и без --force.
6. Гонка: отклонённый push — rc=1 + `[rejected]` в stderr (недоступное
   зеркало — rc=128: НЕ ретраить); bounded retry 3, перед каждым повтором
   ОБЯЗАТЕЛЕН свежий `fetch` (новый tip нет в локальном odb — commit-tree
   с ним иначе падает «not a valid object»; воспроизведено с force-push).
7. След в корп-репо: только unreferenced-объекты в .git/objects (уходят при
   gc; fsck будет показывать dangling — безвредно) и FETCH_HEAD — как у Э2.

Вывод: секция «Снимок <проект>», kv REPO/MIRROR/BASE, итог ✅ sha7; в цикле
по всем проектам — сводка `N снято, M пропущено, K ошибок` (exit 1, если
попытки были и ВСЕ упали).

## 5. Служебная ветка и формат данных

Дерево `pbx/state` (корень, без подкаталогов):

- **`state.json`** — полное состояние, схема:
  `{"schema":1,"project":…,"generated_at":<epoch>,"host":…,"repo":…,
  "fetch_ok":bool,"origin":…,"base_branch":…,"base_ref":…("origin/dev" —
  реально использованный ref для ahead/behind и лога; "" если его нет),
  "current_branch":…,
  "dirty":N,"in_merge":bool,
  "base":{"sha":…,"date":<epoch>,"subject":…} | null,
  "log":[{"sha7":…,"date":"YYYY-MM-DD","subject":…}×20],
  "branches":[{"name":…,"where":"remote|local","sha7":…,"ahead":N,"behind":N,
  "last_date":…,"shortstat":…}×≤30],"branches_total":N}`.
  Сборка — printf-ами (формат ВСЕГДА литеральный: `printf '%s' "$var"` —
  сабжект с `%` в формате падает/искажается, воспроизведено) с новым
  **`_json_str_v2`**: к `\\` и `\"` добавляются `\t`/`\n`/`\r` и вычистка
  остальных C0 (<0x20) — сырой таб в сабжекте ломает JSON (воспроизведено);
  порядок замен критичен: backslash первым. `_json_str` остаётся для
  status_json (совместимость), v2 — для state.
- **`state.env`** — скаляры KEY=value в стиле `.meta` (читатели — `sed -n
  's/^KEY=//p'`, НЕ source). При записи значения обрезаются до первой строки
  (`${val%%$'\n'*}` — перевод строки в значении инжектит фейковый ключ;
  воспроизведено).
- **`branches.tsv`** — `name TAB where TAB sha7 TAB ahead TAB behind TAB
  last_date TAB shortstat`. Свободный текст — ТОЛЬКО последним полем;
  средние поля никогда не пусты (пустое → сентинель `-`: подряд идущие табы
  схлопываются у `read` и сдвигают поля — воспроизведено).
- **`log.tsv`** — `sha7 TAB date TAB subject` (сабжект последним: внутренние
  табы сабжекта тогда не теряются при `read` с точным числом переменных).

Сбор (всё проверено на фикстуре):
- ветки: `for-each-ref --sort=-committerdate --count=30 --format=
  '%(refname:short)%09%(objectname:short)%09%(committerdate:unix)…%(subject)'`
  по `refs/remotes/origin/{feature,fix,hotfix,bugfix,chore}/*` + локальные
  тех же префиксов, которых нет в origin (`show-ref --verify
  refs/remotes/origin/<имя>` → нет → `where=local`); поле сабжекта —
  `%(subject)`, НЕ `%s` (`%s` молча печатает буквальные «%s»);
- ahead/behind: `rev-list --left-right --count origin/<BASE>...<ветка>` —
  порядок вывода `BEHIND TAB AHEAD` (левое = только в BASE; доказано
  на фикстуре --oneline-ом), читать `read -r behind ahead`;
- shortstat: `diff --shortstat origin/<BASE>...<ветка>`; влитая ветка даёт
  ПУСТОЙ stdout c rc=0 — трактуется «нет изменений» (сентинель `-`);
- лог: `log origin/<BASE> -20 --format='%h%x09%cs%x09%s'`;
- деградация «нет origin/<BASE>»: проверка заранее `show-ref --verify
  --quiet refs/remotes/origin/<BASE>` (rev-list/log/diff иначе fatal 128 и
  убили бы снапшот под set -e) → `base:null`, лог пуст, ветки без
  ahead/behind/shortstat (`-`), `base_ref=''`; corp рендерит предупреждение;
- detached HEAD (`branch --show-current` пуст, rc=0) → `current_branch:""`;
  незавершённый merge (`.git/MERGE_HEAD` существует) → `in_merge:true` —
  сбор жив в обоих случаях (проверено).

## 6. `pbx corp` — механика (проверено вживую)

1. Предпроверка `ls-remote <MIRROR> refs/heads/pbx/state`:
   rc=128 → «зеркало недоступно (VPN/PAT?)»; rc=0 + пусто → «снимка ещё
   нет — запусти `pbx snapshot <проект>` на ноуте»; иначе — читать.
2. tmp-репо: `mktemp -d` → `git init -q` → `GIT_TERMINAL_PROMPT=0 timeout 30
   git fetch --depth 1 <MIRROR> pbx/state` (shallow по file:// и обычным
   URL работает: 6 объектов против всей истории; предупреждение git про
   «--depth ignored in local clones» касается только clone) → чтение
   `git cat-file blob FETCH_HEAD:<файл>` (без checkout; отсутствующий в
   дереве файл — rc=128, обрабатывается как «снимок старой схемы») →
   `rm -rf` tmp (достаточно; цикл stateless — ~0.02 c на фикстуре).
3. Человеку: секция на проект — возраст снимка («N ч назад», >24ч — жёлтое
   «снимок протух»), `fetch_ok=false` — жёлтое «ноут снимал без связи с
   gitlab», tip dev (sha7+дата+сабжект), dirty/in_merge корп-репо, таблица
   веток (имя, where, ahead/behind, дата), последние 10 строк лога dev.
   Нет MIRROR → скип с пометкой (в no-arg) / die (с аргументом).
4. `--json`: массив по проектам:
   `{"project":…,"available":true,"state":<содержимое state.json как есть>}`
   либо `{"project":…,"available":false,"reason":…}` — state.json не
   парсится, встраивается сырым (мы же его и сгенерировали).

Роль в конвейере: перед подготовкой доставки ИИ вызывает `pbx corp <проект>
--json` и сравнивает tip/лог корп-dev с тем, что известно дома (страховка
SUP-2603 на этапе планирования). Автоматическое сравнение дом↔корп — Э4 (ctx).

## 7. push-мета: `meta_update` (кандидат ревью Э2 — включён)

Новая функция `meta_update <файл> KEY=VALUE…` (проверена: 39/39 ассертов на
фикстуре, включая конкурентный smoke 423 чтения × 300 перезаписей без битых):
- обновляет существующие ключи на месте (порядок строк и шапка сохраняются),
  новые — в конец; файла нет → создаёт с шапкой;
- атомарно (tmp+mv), best-effort (warn, не die); ГРАБЛЯ: редиректы
  обрабатываются слева направо — подавление ошибок только группой
  `{ … > "$tmp"; } 2>/dev/null`;
- CR чистится и в аргументах, и в строках существующего файла (meta с
  /mnt/c бывает CRLF — без чистки ключ «COMMIT\r» задваивается;
  воспроизведено); `\n` в значении → пробел; ключи валидируются
  `[A-Za-z0-9_]+` (кривой аргумент — warn и пропуск, файл не портится);
- чтение существующего — `while read || [[ -n $line ]]` (последняя строка
  без \n иначе молча теряется).

`write_pack_meta` переводится на неё (вариант (а) research: pack-ключи
обновляются, чужие выживают — рекомендация по простоте и совместимости).
`cmd_push` после успешного пуша пишет
`PUSHED_AT/PUSH_BRANCH/PUSH_COMMIT/PUSH_SOURCE_COMMIT`.
Читатели (status_collect, collect_diag) обратносовместимы: формат KEY=value
не меняется, каждый прежний ключ встречается ровно один раз. Устаревшие
push-ключи после нового pack — это данные, не баг: читатель сравнивает
PUSH_SOURCE_COMMIT с текущим состоянием (§8).

## 8. MIRROR и push-инфо в `pbx status`

- Человеку: к строке repo добавляется dim-строка
  `mirror: <URL> (push: <ветка> @ <sha7>, <когда>)` — если MIRROR задан;
  push-часть — если есть push-мета; если PUSH_SOURCE_COMMIT ≠ текущий HEAD
  SRC — приписка `SRC ушёл вперёд` (бесплатный детект устаревшего пуша).
- `--json`: в конец объекта — `"mirror":"…","push_branch":"…",
  "push_commit":"…","pushed_at":N` (сентинели: '' / -1). Порядок прежних
  ключей не меняется (совместимость потребителей).

## 9. Меню

Два пункта после `deliver`:
`snapshot — снимок корп-состояния в зеркало (ноут)` и
`corp     — корп-состояние проектов (дом)`.
Оба вызывают no-arg вариант (обход всех проектов): snapshot — пишущая
команда → выход из меню; corp — read-only → menu_pause → возврат в меню.
«выход» становится 12-м; ВСЕ меню-тесты с цифровым вводом пересматриваются
(как в Э2).

## 10. Чего НЕ делаем (Э3)

- Автосравнение дом↔корп и агрегированный контекст — Э4 `pbx ctx`.
- MR-статусы из GitLab API (нужен корп-токен) — вне охвата.
- Создание зеркал (gh repo create) — руками, как в Э2.
- Историю снимков не читаем (только tip `pbx/state`); ротацию/сквош истории
  ветки не делаем (дерево маленькое, история дешёвая).
- diff содержимого веток (кроме shortstat) — не тащим.
- Скип «пустого» снапшота — осознанно нет (§2.1 п.7).

## 11. Тестирование (TDD; все сетевые — на локальных bare-репо file://)

1. `meta_update`: создание/мерж/атомарность/шапка; pack→push→pack —
   push-ключи выживают; значения с пробелами/кириллицей/`=`; CRLF-файл
   нормализуется; кривые ключи не портят файл.
2. `_json_str_v2`: таб/CR/C0 в сабжектах; порядок замен; python3 -m
   json.tool как валидатор в тестах.
3. Сбор состояния на фикстуре (bare-«gitlab» + REPO + ветки всех классов:
   ahead/behind, влитая, local-only, remote-only): числа behind/ahead в
   правильном порядке; local-only помечены; влитая — shortstat `-`;
   сабжекты с кавычками/кириллицей/`%`/табом не ломают JSON и TSV;
   деградации: нет origin/dev → base:null; detached HEAD; in_merge.
4. `cmd_snapshot` e2e на bare-зеркале: ветка `pbx/state` создаётся
   root-коммитом; второй снапшот — fast-forward без --force;
   **корп-коммиты в зеркало НЕ утекли** (`git -C mirror cat-file -e
   <corp-sha>` падает — ключевой тест); корп-репо бит-в-бит не тронут
   (status --porcelain + sha1sum индекса до/после); сбой fetch origin →
   fetch_ok=false, снимок состоялся; недоступное зеркало → die без ретраев;
   без MIRROR → die/скип по режиму; гонка (чужой push между fetch и push) →
   retry с повторным fetch побеждает, чужой коммит цел.
5. `cmd_corp` e2e: рендер с фикстурного зеркала; `--json` валиден
   (python3 -m json.tool) и содержит state как есть; нет ветки → «снимка
   ещё нет»; недоступное зеркало → «зеркало недоступно»; протухший снимок
   (generated_at в прошлом) → warn; fetch_ok=false → warn; tmp-репо убран.
6. status: новые JSON-ключи в конце, прежний порядок цел; dim-строка mirror;
   `SRC ушёл вперёд` при PUSH_SOURCE_COMMIT ≠ HEAD.
7. Меню: перенумерация всех цифровых вводов, оба новых пункта.
8. Регресс: полный прогон существующих 279 ассертов.

## 12. Критерии приёмки

1. На фикстуре «ноут»: `pbx snapshot` кладёт валидные state-файлы в
   `pbx/state` зеркала; корп-история в зеркало не утекает; корп-репо не тронут.
2. На фикстуре «дом»: `pbx corp` показывает состояние; `--json` валиден;
   деградации (нет снимка/нет MIRROR/недоступно/протух) — понятные сообщения.
3. push-мета живёт в `.meta`, переживает pack и видна в status; MIRROR в status.
4. Все тесты зелёные; plain-инварианты не задеты; один bash-файл; README
   дополнен (обратный поток, ритуал: конец дня на ноуте — snapshot, дома
   перед доставкой — corp; PAT тот же, что для Э2).
